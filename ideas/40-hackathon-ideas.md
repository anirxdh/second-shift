# 40 Multi-App AI Agent Ideas — Updated and Ranked

Updated September 13, 2026 after the organizers' clarification, as relayed by the user. This version supersedes the previous voice/3D-led ranking. Original idea IDs are retained so earlier discussions remain easy to map.

## What changed

- **Sponsor products are optional.** Arga, Lemma, Userlens, Clera, and Comma are not required components. Their catalogs do not define which apps we can use.
- **Priorities: real-world usefulness, creative problem-solving, and substantial technical execution.** A product does not need to be playful. Novelty should come from what it solves or how it works.
- **Ambitious visions remain.** We can demonstrate one complete happy path through a larger product, without claiming the unimplemented vision already works.
- **Voice and 3D are optional interface choices.** They receive no ranking bonus. Prefer a clear conventional interface unless voice helps someone work hands-free or a spatial view explains an actual spatial dependency.
- Every concept must meaningfully connect at least **three external apps**. Multiple endpoints in one app do not become multiple apps. A local database or a visual library does not count as an external app.
- Use direct provider APIs, connectors, or available test environments as appropriate. Test data and simulated integrations must be labeled. Tool availability, authentication, pricing, and exact endpoint coverage need confirmation for the selected workflow.
- The earlier paid-tier assumption is a budgeting assumption, not a promise of credits for any newly chosen vendor.

## Ranking method

The ranking considers the published criteria: **30% technical execution, 25% reliability/evaluation, 20% usefulness, 15% originality, and 10% demo clarity**. It is a holistic ordinal assessment, not a computed score or a forecast of judging results. There are no measured user-demand or competition scores behind it.

I favor a clear user and useful outcome, meaningful engineering beyond sequential API calls, explicit success conditions, and an understandable demonstration. Among similarly strong ideas, a distinctive mechanism and attainable data/integration access break ties. The rank reasons name material limitations rather than claiming every idea is excellent.

**Technical depth** can come from constraint solving, reconciliation, content transformation, provenance, concurrency, approval/version control, and reliable multi-system execution. Adding more agents, more apps, or a 3D scene is not itself evidence of depth.

The LLM can interpret messy inputs and explain proposals. Deterministic code should validate rules, compute money/quantities, enforce state transitions, and check final records where possible.

**Evidence in the happy-path demo:** use real tool calls against the declared environment, read back final records, and repeat from a clean fixture. Stronger evidence can add one negative case, but the video can stay focused on the successful journey. Repeating one fixture proves repeatability for that fixture, not general reliability. Each idea below includes its proof target and prospective evaluation scope.

## My current recommendation

**Start by comparing Exit Rehearsal, Promise Keeper, and Second Shift.**

- **Exit Rehearsal:** strongest combination of technically substantive work and objectively inspectable output. Its first contract should state exactly which source block types and links are supported.
- **Promise Keeper:** strongest cross-team commercial reasoning angle. It needs explicit, labeled commitments so the demo can distinguish evidence from interpretation.
- **Second Shift:** strongest immediate operational outcome. It needs a real constraint model, not a model-generated schedule accepted without checking.

**Unblock** is the industrial option if we can obtain credible production fixtures. **Tomorrow** is the ambitious scenario-planning option if we can specify its dependency model accurately. Tomorrow moves from first to fifth because its simulation is harder to validate, not because ambition is undesirable.

These are candidates for the user's decision. None has been selected, market-validated, or fully integration-tested.

### Rank 1. Exit Rehearsal — original idea #39

**User and problem:** A small team moving one active project from Notion into Google Docs.

**Updated product vision:** A software exit navigator that maps selected work, rehearses a migration, verifies what survives, and coordinates the team's transition with a recoverable source.

**Three-plus-app workflow:** **Notion:** source project content and checklist state. **Google Docs/Drive:** destination document and stored migration manifest. **Slack:** find selected project references and publish the approved handover. Count Notion, Google Docs, and Slack as the three core apps; Drive is supporting storage.

**What makes this technically substantial:** Build a content migration compiler: recursively discover the selected source, normalize supported blocks into an intermediate format, map internal references, write the destination, and reconcile it against a content manifest. Track each write so retries resume instead of duplicating sections. Keep the source until the user accepts the migration.

**Complete happy-path demo:** Read a selected Notion project, create its supported Docs/Drive destination, verify a content manifest, identify project references in a designated Slack channel, and publish an approved handover.

**How we know it worked:** All supported source blocks and checklist states match the destination manifest; every selected internal link resolves; unsupported content is reported. Re-running produces no duplicate document. Permissions are explicitly reviewed rather than assumed equivalent.

**Interface:** Use a source/destination diff, supported-content manifest, unresolved-items list, and verified handover status. A migration animation is optional.

**Why rank 1:** Best combination of useful outcome, substantial engineering, distinctive approach, and machine-checkable success. Rich content and permission differences are the main scope risk.

### Rank 2. Promise Keeper — original idea #29

**User and problem:** **Promise Keeper:** Sales has promised a customer something engineering may not be able to deliver.

**Updated product vision:** A customer commitment control center connecting commercial promises, delivery work, internal decisions, and external communication.

**Three-plus-app workflow:** **HubSpot:** customer commitments and account identity. **GitHub:** delivery issues and milestones. **Slack:** explicit internal decisions. **Gmail:** approved customer clarification. A CRM alternative is possible if direct API access is easier; sponsor coverage is not a constraint.

**What makes this technically substantial:** Extract explicit customer commitments with source spans and dates, resolve them to engineering issues, build a versioned dependency graph, and compare required delivery conditions with observed milestone state. Separate an explicit promise, a suggested date, and a model inference. Route discrepancies to the accountable person with a proposed action.

**Complete happy-path demo:** Find an explicit promise in HubSpot, reconcile it with GitHub milestones and Slack decisions, then draft a cited Gmail clarification for the account owner to approve.

**How we know it worked:** Each flagged mismatch cites the original commitment and engineering record. A labeled fixture set checks precision and recall; tentative language must not become a confirmed promise. The approved follow-up references the correct customer and issue.

**Interface:** Use a focused workflow with source evidence, a reviewable proposed action, and verified completion state. No voice, game, or 3D feature is required.

**Why rank 2:** Strong commercial problem with interesting cross-system reasoning. Ranks below migration because interpreting promises and delivery feasibility is less objectively verifiable.

### Rank 3. Second Shift — original idea #3

**User and problem:** **Second Shift:** A technician calls out, leaving a small service business with customers expecting visits.

**Updated product vision:** An adaptive dispatch center that reorganizes a service business's day around staff, qualifications, equipment, and customer commitments.

**Three-plus-app workflow:** Matches jobs and qualifications from **Sheets** to availability in **Calendar**, proposes reassignment, then sends approved **Gmail** updates and **Slack** assignments.

**What makes this technically substantial:** Represent qualification, service duration, time windows, equipment, and travel buffers as constraints. Use a constraint solver or deterministic search to assign feasible jobs; use the model to interpret requests and explain trade-offs. Recheck calendar state immediately before committing the approved schedule.

**Complete happy-path demo:** A technician becomes unavailable. Read job requirements in Sheets, assign an available qualified replacement in Calendar, notify the crew through Slack, and confirm the revised visit through Gmail.

**How we know it worked:** Every assignment satisfies the declared constraints; no technician is double-booked; protected appointments remain unchanged. Verify calendar events and recipient-specific notifications. Travel buffers are supplied estimates unless a routing provider is actually integrated.

**Interface:** Use a clear schedule, resource table, and action/evidence panel. Voice may help a hands-busy operator. Add a spatial view only if physical layout or resource placement materially affects the decision.

**Why rank 3:** Clear operational value and visible technical execution. The scheduling model is demonstrable, but realistic staff and travel data are essential.

### Rank 4. Unblock — original idea #1

**User and problem:** **Unblock:** A small workshop cannot complete an order because one part or resource is missing.

**Updated product vision:** A production control room that connects customer orders, parts, suppliers, staffing, and delivery commitments across a workshop or factory.

**Three-plus-app workflow:** **Google Sheets:** structured orders, stock, and capacity for the initial demo; an ERP could replace it later. **Gmail:** supplier commitments. **Google Calendar:** production reservations. **Slack:** recovery assignments. Do not claim an ERP integration until implemented.

**What makes this technically substantial:** Model orders, bills of material, inventory, supplier lead times, and production capacity as a dependency graph. Detect the changed dependency, compute which orders it affects, and search approved substitutions and rescheduling options. Persist an action plan that coordinates writes and verifies each step.

**Complete happy-path demo:** A supplier delay threatens an order. Read stock in Sheets, find an approved supplier alternative in Gmail, revise the production booking in Calendar, and publish the recovery assignment in Slack.

**How we know it worked:** No plan consumes the same inventory twice, selects an incompatible part, or exceeds declared capacity. Delivery estimates use explicit fixture assumptions. Read back revised bookings and assigned recovery work.

**Interface:** Use a focused workflow with source evidence, a reviewable proposed action, and verified completion state. No voice, game, or 3D feature is required.

**Why rank 4:** Ambitious and deeply technical with a concrete industrial use case. Below dispatch because manufacturing assumptions and source data are harder to establish quickly.

### Rank 5. Tomorrow — original idea #31

**User and problem:** A small event or workshop organizer with a plan scattered across apps.

**Updated product vision:** An operational scenario-planning and execution system. Build an explicit model of commitments from connected records, rehearse a defined disruption, compare feasible repairs, and execute the approved plan with source-state revalidation.

**Three-plus-app workflow:** Read the room and session schedule from **Calendar**, equipment requirements and backup stock from **Sheets**, and confirmed supplier commitments from **Gmail**. Apply an explicitly selected hypothetical failure to a copy of that state. Identify the affected session, search the approved backup inventory, and draft a recovery plan in **Docs**. After approval, reserve the alternative in Calendar and notify the designated staff through Gmail.

**What makes this technically substantial:** Create an explicit operational model from source records, fork a versioned scenario, apply one user-selected counterfactual, and recompute dependent constraints. Compare feasible recovery plans. At approval time, revalidate the real source version and apply only the approved changes through an execution ledger.

**Complete happy-path demo:** Tour an upcoming event using Calendar, Sheets, and Gmail; simulate a supplier cancellation in an isolated scenario, find an available backup, produce the Docs recovery plan, then reserve and notify after approval.

**How we know it worked:** Hypothetical writes remain isolated; impact follows declared dependencies; the chosen repair satisfies constraints; stale source data invalidates the proposal. Final external records match the approved difference between plans.

**Interface:** Start with a dependency graph and side-by-side scenario diff. A 3D view is optional and cannot substitute for a valid operational model. Distinguish hypothetical and actual state.

**Why rank 5:** Most ambitious simulation concept in the collection. Strong originality, but only credible when its dependency model is explicit; visual simulation alone does not establish real-world predictive accuracy.

### Rank 6. Invoice Gate — original idea #10

**User and problem:** **Invoice Gate:** A business receives an invoice that does not match what it ordered.

**Updated product vision:** A purchasing review desk that connects orders, delivered goods, vendor correspondence, and invoice approval into an inspectable chain.

**Three-plus-app workflow:** Compares the **Gmail** invoice with purchase records in **Sheets** and receipts in **Drive**, then requests review through **Slack**. It does not pay invoices.

**What makes this technically substantial:** Extract invoice line items, match vendor and order identities, and reconcile quantity, unit price, currency, and delivery evidence across systems. Use deterministic arithmetic and duplicate fingerprints. Produce a review package with exact source evidence for discrepancies.

**Complete happy-path demo:** Read an invoice in Gmail, match it with a purchase record in Sheets and receipt in Drive, then send a cited review request to Slack with the proposed disposition.

**How we know it worked:** Known duplicates and fixture mismatches are identified without inventing fraud conclusions. Arithmetic reconciles exactly; approval is requested for the correct order. Include legitimate near-matches when evaluating false positives.

**Interface:** Use a focused workflow with source evidence, a reviewable proposed action, and verified completion state. No voice, game, or 3D feature is required.

**Why rank 6:** Highly useful and objectively testable. Lower originality than the top ideas; differentiation must come from evidence reconciliation and handling ambiguous matches.

### Rank 8. ChangeOrder — original idea #2

**User and problem:** **ChangeOrder:** Freelancers lose money when “one small change” becomes unpaid work.

**Updated product vision:** A commercial operating layer for creative agencies: track scope, detect changes, assemble approved proposals, and keep delivery and billing aligned.

**Three-plus-app workflow:** Compares a new **Gmail** request against the agreed scope in **Docs**, drafts a priced change proposal, and creates a **Stripe** invoice after approval.

**What makes this technically substantial:** Version agreed scope into structured deliverables and exclusions with citations. Map incoming requests onto that scope, distinguish revisions from additions, and use a user-approved rate card to construct the change proposal. **Complete happy-path demo:** A client requests three extra deliverables. Compare Gmail against the signed scope in Docs, draft the change proposal, obtain approval, and create the matching Stripe invoice with a linked delivery checklist.

**How we know it worked:** Every charge cites a new requested deliverable and an approved rate; totals are computed deterministically. Invoice creation happens once and reflects the approved version. Ambiguous scope goes to review.

**Interface:** Use a focused workflow with source evidence, a reviewable proposed action, and verified completion state. No voice, game, or 3D feature is required.

**Why rank 8:** Direct business value and a clear demo. Less technically distinctive unless the scope-difference and approval machinery is substantive.

### Rank 9. Paper Trail — original idea #30

**User and problem:** **Paper Trail:** Teams cannot establish who approved a change and what happened afterward.

**Updated product vision:** An evidence navigation layer that reconstructs how decisions move across people, documents, tasks, and communications.

**Three-plus-app workflow:** Connects a **Gmail** approval to the relevant **Drive** document version and **Linear** task; produces a linked evidence record in **Docs** with gaps explicitly marked.

**What makes this technically substantial:** Build a provenance graph joining decisions, document versions, task changes, and explicit approvals. Preserve source IDs and timestamps. Resolve conflicting records into a cited chronology without treating timestamp proximity as proof of causation.

**Complete happy-path demo:** Connect a Gmail approval to the exact Drive version and related Linear task, then produce a Docs evidence record with clickable sources and unresolved gaps.

**How we know it worked:** Each asserted relationship is backed by an explicit reference or labeled inference. Known missing links remain gaps; the generated record points to the correct versions rather than just the latest document.

**Interface:** Use a focused workflow with source evidence, a reviewable proposed action, and verified completion state. No voice, game, or 3D feature is required.

**Why rank 9:** Strong auditability and technical depth. Slightly weaker immediate action outcome: make the evidence package resolve a specific pending decision, not merely visualize history.

### Rank 10. Time Heist — original idea #38

**User and problem:** A tutor or repair workshop with an opt-in waiting list.

**Updated product vision:** A cancellation recovery network that matches newly available appointments to pre-consenting waitlists and completes a fair, confirmed rebooking workflow.

**Three-plus-app workflow:** Verify the cancelled slot in **Calendar**, read the waitlist and service-duration rules in **Sheets**, and inspect explicit availability preferences from **Gmail**. Offer the slot to one eligible person at a time under a clear hold policy. After they accept, recheck availability, book the slot, update their waitlist status, and confirm through Gmail.

**What makes this technically substantial:** Implement a slot-offer state machine with eligibility rules, an explicit queue policy, expiring holds, and idempotent acceptance. Coordinate offers in a transactional local ledger, then recheck provider state before booking; account for external calendar edits.

**Complete happy-path demo:** Detect an open Calendar slot, match duration and eligibility in Sheets to explicit Gmail preferences, obtain one acceptance, recheck the slot, reserve it, and update the waitlist.

**How we know it worked:** Only one eligible person receives the confirmed slot; late or repeated acceptances cannot duplicate bookings. Waitlist state agrees with the calendar and sent confirmation. Test controlled concurrent acceptance as follow-up evidence.

**Interface:** Use a focused workflow with source evidence, a reviewable proposed action, and verified completion state. No voice, game, or 3D feature is required.

**Why rank 10:** Excellent concurrency and consistency problem with obvious usefulness. Familiar market category reduces originality; policy-aware coordination must be the distinguishing feature.

### Rank 15. Sorry, Fixed — original idea #35

**User and problem:** A small business that sent a customer the wrong appointment time and must repair the surrounding records.

A few primary-source checks ground the leading technical directions:

- Notion documents nested page blocks and paginated retrieval. Exit Rehearsal must account for both rather than assume one request contains the whole project. [Notion page content guide](https://developers.notion.com/guides/data-apis/working-with-page-content)
- Google Calendar exposes a free/busy query. This can supply scheduling inputs; it does not itself solve resource constraints or make a sequence of bookings transactional. [Google Calendar free/busy reference](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query)
- GitHub documents permission requirements for managing check runs. If onboarding or engineering evidence uses checks, access must be configured; this is not automatically available merely because a repository can be read. [GitHub Checks guide](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-checks)

Those checks do not establish a complete migration, scheduling, or onboarding integration. The selected journey still needs an endpoint-by-endpoint authentication and capability check.

## Definition of a credible first demonstration

1. One explicit user request and a useful completed outcome.
2. At least three external apps each contribute necessary records or actions.
3. The agent interprets the request and uses working tools; important calculations and constraints have executable checks.
4. Required user review and other participants' acceptance remain part of the happy path. Seeded replies are declared fixtures.
5. The backend records action IDs, attempts, results, and verification so the interface reports actual state.
6. The demo ends with the external artifacts and measured fixture results, not only a success animation.
7. Broader ambition is clearly labeled as the product direction. There is no claim of production readiness from one curated path.

No sponsor tool is required. No product has been selected. The user will choose after reviewing the updated ranking.
